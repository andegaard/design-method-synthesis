# Dataset manifest: design-method-synthesis

Every file in `environment/data/` is synthetic, generated by a deterministic script in
this directory. Each generator is idempotent: it leaves an existing file alone if that
file already reproduces the sealed ground truth (`tests/ground_truth.json`) within
tolerance, and only writes a fresh version otherwise. `generate_ground_truth.py` (one
level up) runs all five, then runs `solution/solve.py` against the result and grades it
with the exact checks in `tests/test_outputs.py`, in-process.

None of the five stages uses random sampling anywhere in the shipped data: every file is
either a fully deterministic scored/structured chart, a closed-form problem statement, or
built from named (not randomly drawn) conditions, so the whole dataset is exactly
reproducible and every generator's self-check is a real independent re-derivation, not a
tolerance check against its own random seed. Every numeric value in every file --
sub-function scores, FR-DP matrices and process capabilities, the spring's force,
deflection, material, buckling, temperature, wire-treatment, and actuation-rate/frequency-
margin requirements, the fatigue-life-philosophy background data, the Taguchi factor
levels, and the final-design candidates -- was authored from scratch for this task; none
of it reproduces a textbook or literature problem instance, and every constant is
independently verified (by multistart numerical re-solution, not just re-typed) to be
physically consistent with every other constant.

## Physics given, not spelled out

`spring_optimization_problem.json`'s `physical_relations` field goes one step further
than "physical facts, not inequalities": for every relation with a single, standard,
uniquely-named textbook form -- the Wahl stress-concentration factor, the peak-shear-stress
relation, the spring-rate relation, the linear/Goodman fatigue mean/alternating-stress
damage criterion (named as such, with its structure described in words -- normalize
alternating stress against the endurance limit, mean stress against the ultimate strength,
sum, bound by the safety factor -- but never written as `tau_a/S_se + tau_m/S_su <=
1/n_f`), Turner's composite effective-CTE homogenization model, a rule-of-mixtures
composite-density relation, and the fundamental-natural-frequency (spring-surge) relation
-- the data file names the principle and the quantities it depends on and stops there;
supplying the exact closed form is left entirely to whoever solves the task. There is no
`g1(d, D, Na) <= 0` anywhere in the shipped data, and no `Kw = (4C-1)/(4C-4) + 0.615/C` or
`f_n = (2/pi)*(d/(D^2*Na))*sqrt(G/(32*rho))` either. The one relation still spelled out as
an explicit equation is the composite's thermal-residual-stress estimate: unlike Turner's
model, there is no single universally-agreed closed form for a constrained-mismatch
residual-stress estimate in a particulate composite, so leaving it unstated would make the
task depend on which of several defensible variants the solver guessed, not on genuine
expertise -- it stays explicit for the same reason the free-length/buckling geometry does
(`Ls = (Na+2)*d`, `L0 = Ls + delta_req_mm + clash_allowance_mm`): both are task-specific
bookkeeping a reference could not supply, not textbook material an expert is expected to
already know. A second relation, Basquin's finite-life fatigue equation
(`tau_a_allow(N) = tau_f' * (2N)^b`), *is* named as a standard textbook form (it is), but
its two material constants (`tau_f'=1650.0 N/mm^2`, `b=-0.09`) are given directly rather
than left to a lookup table, since they are specific to this composite wire and not a
value any general reference would supply. No material properties or buckling limit are
given as bare numbers either: both are small tables (`material_options`,
`end_fixation_buckling_limits`) keyed by the variant codes from `morphological_chart.json`,
so using them correctly requires carrying the concept-selection stage's own winning
combination forward. Each `material_options` row also carries its two constituent phases'
own CTE, bulk modulus, mass density, and (matrix) Young's modulus rather than a single
already-homogenized number for each, so the composite's effective CTE, residual stress, and
homogenized density are themselves outputs of a derivation, not lookups. `D3`, the row the
concept-selection stage always picks, goes one step further and omits its own
`S_su_Nmm2`/`S_se_base_Nmm2`/`tau_allow_Nmm2` entirely -- unlike `D1`/`D2`, which still give
them directly -- since this alloy's strength depends on a post-consolidation temper choice;
see "The tempering trap" below. `instruction.md`
does not walk through any of these formulas in prose either, named or algebraic -- it only
states what must be derived and reported; the physical relations, however specific, live
solely in this data file. This is a deliberate difficulty lever, not an incidental one: a
solver that does not already command the Wahl factor, the Goodman fatigue interaction, or
the fixed-fixed spring-surge frequency relation at the level a mechanical-design or
composite-materials specialist would cannot pass by pattern-matching the given text onto a
formula, because no formula is given to pattern-match onto.

Three requirements go further still, asking for something other than a derivation from
stated physics:

- **The process-robustness noise magnitude is not given anywhere in
  `spring_optimization_problem.json` or `instruction.md`.** It exists only as an emergent
  property of `taguchi_spring_robustness.csv`'s raw, per-run, per-noise-condition spring-
  rate measurements, recoverable by inverting the standard spring-rate relation against
  them. See "The process-robustness re-check" below.
- **Which fatigue-life criterion governs the frequency-optimized alternative is a genuine
  judgment call, not a computation.** Both criteria (infinite-life and Basquin finite-life)
  are given; nothing in the data states which one applies to this alternative design. See
  "The fatigue-life-philosophy judgment call" below.
- **The selected material's own strength properties are not given at all, as a number or a
  formula.** They must be read off `tempering_response` at whichever tempering temperature
  both clears a stated Charpy toughness floor and, jointly with the wire-treatment choice,
  minimizes cost -- a second discrete search axis layered on top of the wire-treatment
  search, not a derivation from any named physical relation. See "The tempering trap" below.

`authoring/provenance/dataset/generate_spring_opt.py` and `solution/solve.py` both derive
the same eleven constraint functions -- five static/geometric, the fatigue criterion,
buckling, the frequency floor, and the three process-robustness re-checks, including the
composite-derived residual-stress term inside the fatigue constraint and the composite-
density-derived natural-frequency floor -- from those facts independently (written
separately, not shared code), and agree with each other and with the sealed optimum to
high precision. Both files, independently, also cross-check their own optimum with a
second, genuinely independent differential-evolution solve of the actual cost objective (not
merely a feasibility search) rather than only asserting multistart agreement -- the actual
guarantee that the physics admits exactly one well-posed constraint set and one well-posed
cheaper-treatment choice, not that the instructions merely assert one. None of these DE
calls share a seed across files: the generator's own warm-start search uses seed 0 and its
cross-checks use seed 11; `solution/solve.py`'s warm-start search uses seed 5 and its own
cross-checks use seed 23 -- so agreement between the two files is never an artifact of both
having drawn the same random search path.

## The Independence Axiom gate: a genuine discriminator

`generate_axiomatic.py` builds three candidate embodiments of the same subsystem. X
(decoupled) and Z (uncoupled) both satisfy the Independence Axiom; Z has the tightest
process data of *those two* and would be the naive Information-Axiom winner if X were not
even tighter. Y is fully coupled -- its FR-DP matrix cannot be reordered into a triangular
form -- but its process data is deliberately the tightest of all three designs
(`sigma` roughly half of X's on every FR), giving it the lowest raw information content of
the three. A correct application of Axiomatic Design rejects Y outright on the
Independence Axiom, before information content is ever compared, leaving X as the
recommended design (0.0240 bits, vs. Z's 0.1676 bits). An analysis that computes
information content for all three designs and simply picks the minimum -- skipping the
coupling gate, or applying it after ranking by information content instead of before --
would wrongly recommend Y. `tests/test_outputs.py::test_axiomatic_coupled_design_excluded_from_information_axiom`
checks this directly: Y must not even appear as a key in `information_content_bits`.

## The robustness-vs-on-target distinction

`generate_taguchi.py`'s noise model is deterministic by design: the outer array is three
named conditions (a cold/under-count case, nominal, and a hot/over-count case), not random
draws, because the spring-rate relationship `k = G*d^4/(8*D^3*N)` is genuinely, not just
numerically, more sensitive to `d` (4th power) than to `N` (inverse) or `D` (held
noise-free throughout, deliberately, to see whether the resulting response table shows a
factor with essentially no effect on robustness -- it does: factor B's level-average SN
spread is under 0.6 dB, against roughly 4.9 dB for A and 3.4 dB for C). The factor-level
combination that maximizes signal-to-noise (A3/B2/C1, run 8's factor pattern) is *not* the
same combination that minimizes quality loss against the stated 6.0 N/mm target with loss
coefficient 2.5 (that optimum is run 7's pattern, A3/B1/C3) -- maximizing robustness to
noise and hitting a specific target are different objectives, and this dataset is built so
they genuinely diverge rather than coincide, as they easily could by chance on a smaller
or less deliberately shaped experiment. `taguchi_most_robust_equals_best_on_target_true`
is sealed to `false`.

## The process-robustness re-check reuses the Taguchi stage's own hidden noise

`generate_taguchi.py` perturbs wire diameter by `DD_NOISE_MM=0.015` mm and active-coil
count by `DN_NOISE=0.2` coils to build its `low`/`nom`/`high` noise conditions (mean coil
diameter `D` stays noise-free throughout, for the same reason it is held noise-free in the
robust-design analysis itself). Neither number is written down anywhere the parametric-
optimization stage's own data lives -- not in `spring_optimization_problem.json`, not in
`instruction.md`. The only way to recover them is to invert the standard spring-rate
relation `k = G*(d+dd)^4/(8*D^3*(N+dn))` against `taguchi_spring_robustness.csv`'s raw
`low`/`high` spring-rate measurements for each of its nine runs -- exactly what
`solution/solve.py::_derive_process_noise` does, with a nonlinear least-squares fit over
all eighteen non-nominal rows at once, recovering `dd~0.015`, `dn~0.2` to high precision
without ever being told those are the target values. A solver that treats the Taguchi
stage's CSV as belonging only to that stage, and reports the parametric-optimization
result without this re-check, has silently skipped an entire requirement rather than
merely under-specified one.

The three re-checks this noise feeds do not all fail in the same perturbation direction,
which is itself part of the required reasoning, not a detail to copy: `g9_fatigue` depends
only on wire diameter (the fatigue relation has no `Na` dependence at all), and is worst at
a *thinner* wire (`d - dd`); `g9_buckling` is worst at a *thicker* wire together with *more*
coils (`d + dd`, `Na + dn`), since both raise the spring's free length; `g9_freq` is worst
at a *thinner* wire together with *more* coils (`d - dd`, `Na + dn`) -- the same coil
direction as buckling, but the opposite wire-diameter direction, because thinner wire
lowers natural frequency while it raises free length only through solid height, not
through this ratio. A single worst-case perturbation applied uniformly to all three would
get at least one of them wrong. At the true global optimum, this re-check is not a slack
formality: the process-robustness fatigue re-check (`g9_fatigue`), not the nominal fatigue
check itself, is what is essentially exactly binding (margin ~1e-10) alongside the
force-delivery oversupply cap -- the nominal fatigue check alone still has about 0.023 of
slack. See "The composite residual-stress trap" below for the full before/after story.

## The fatigue-life-philosophy judgment call

The frequency-optimized alternative -- the design that maximizes natural frequency under
the minimum-cost design's own wire treatment and a cost cap of 1.15x its cost, everything
else held to the same requirements except the frequency floor itself -- is checked against
whichever of two given fatigue criteria the solver chooses: the infinite-life endurance-
limit criterion the minimum-cost design always uses (never itself a judgment call, so that
the headline, most-checked result never hinges on one), or a Basquin finite-life criterion
pinned to a stated `rated_qualification_cycles=50000`. Nothing in the data dictates which
one governs this alternative; `instruction.md` states this explicitly as "a genuine
judgment call with no single correct answer" and asks the report to pick one and justify
it, then report `frequency_alternative_fatigue_philosophy` as `"infinite_life"` or
`"finite_life"`.

On this dataset the two choices produce two different, well-separated designs, not a
rounding-level difference:

| | `d` (mm) | `D` (mm) | `Na` | cost | `f_n` (Hz) | margin ratio |
|---|---|---|---|---|---|---|
| infinite-life | 1.580261 | 14.0 | 4.915110 | 715.823441 | 618.120786 | 30.906 |
| finite-life | 1.542569 | 14.0 | 4.462688 | 637.458189 | 664.547234 | 33.227 |

The finite-life criterion is less conservative here (the Basquin-derived allowable
alternating stress at 50,000 cycles, ~790.3 N/mm^2 after the treatment multiplier, exceeds
the infinite-life endurance limit, ~511.7 N/mm^2), which is *why* it buys both a lower cost
and a higher frequency at once, not a coincidence -- fatigue stops being the design's
limiting concern under this criterion, so the optimizer can push the design further toward
its other limits instead. Recomputing the active-constraint set at each alternative
confirms this directly: the infinite-life design is limited by the housing-bore cap
(`D=D_max`), the force-delivery oversupply cap, and its own process-robustness fatigue
re-check; the finite-life design is limited by the housing-bore cap, the oversupply cap,
and the *static* stress limit instead -- fatigue (nominal or process-robustness) is not
even close to binding there. Neither branch spends its full 15% cost allowance
(`715.82`/`637.46` against a cap of `776.93`): the housing-bore and force-delivery-cap
requirements, not the cost budget, are what actually limit how much dynamic margin is
purchasable, whichever philosophy is used.

Because this is a genuine judgment call, `tests/test_outputs.py::test_frequency_optimized_alternative`
grades it self-consistently: it reads the report's own
`frequency_alternative_fatigue_philosophy` field, selects the matching sealed target
(`freq_alt_infinite_*_true` or `freq_alt_finite_*_true`), and recomputes every non-frequency
requirement under that same chosen philosophy -- so either well-justified choice passes in
full, and a report cannot be marked wrong for choosing the criterion the reference solution
did not happen to pick. This was verified directly, not merely asserted: a `design_report.json`
constructed by swapping every alternative-design field and the `frequency_alternative_fatigue_philosophy`
value to the *other* philosophy's sealed numbers, with the synthesis explanation's
philosophy language swapped to match, was run through the identical grading harness and
also passed all 36 checks.

## The composite residual-stress trap

The selected material row (D3) is a particulate metal-matrix composite wire: an
iron-chromium-alloy matrix phase reinforced with a hard ceramic-like particulate phase at a
24% volume fraction. The two phases contract by different amounts on cooling from the
composite's ~600 C consolidation temperature down to the 20 C reference temperature (matrix
CTE 1.08e-5/C vs. reinforcement CTE 5.6e-6/C), which locks a thermal residual stress into
the matrix -- estimated here as `sigma_res = (V_r/(1-V_r)) * E_m * (alpha_m-alpha_r) *
(T_process-T_ref)` (~197.2 N/mm^2), converted to a shear-equivalent by the von Mises
relation (`tau_res = sigma_res/sqrt(3)`, ~113.8 N/mm^2). This is fixed by the composite's
own processing history, so it applies to the fatigue criterion's mean-stress term
regardless of wire treatment or operating temperature -- it is not a decorative extra
calculation: adding it raises the minimum cost by about 14.8% (675.59 vs. 588.70 without
it) and changes the optimal geometry measurably. It also changes *which* requirement is
active at the optimum, and does so twice over: without the residual stress, the
active-constraint set is {static stress, force-delivery oversupply cap}; adding it moves
fatigue into the active set as the summary result would predict -- but because the
process-robustness re-check of fatigue is now also part of the requirement set, it is that
re-check (`g9_fatigue`, evaluated at the noise-worst-case thinner wire), not the nominal
fatigue check itself, that ends up essentially exactly binding alongside the oversupply
cap, with the nominal check still carrying about 0.023 of margin. A solution that gets the
mechanical spring sizing exactly right, includes the residual stress, but stops at the
*nominal* fatigue check without the process-robustness re-check will therefore still land
on a design that looks feasible and is not, in fact, the true optimum. Turner's model
(`alpha_eff = (V_m*K_m*alpha_m + V_r*K_r*alpha_r) / (V_m*K_m + V_r*K_r)`) gives this same
material's homogenized effective CTE (~9.098e-6/C) as a separately required, separately
graded result -- a genuine, if smaller, composite-micromechanics derivation in its own
right, independent of whether it moves any downstream decision.

## The tempering trap

The selected material's own strength properties (`S_su_Nmm2`, `S_se_base_Nmm2`,
`tau_allow_Nmm2`) are not given as a single set of numbers in `material_options["D3"]` at
all -- unlike `D1`/`D2`, that row omits them entirely, and they must instead be read off
`tempering_response`, a seven-row table (`temper_temp_C`, `hardness_HRC`, and the same
three strength fields, plus `charpy_impact_J`) giving this same matrix alloy's properties at
seven discrete tempering temperatures from 200 C to 600 C. `requirements.charpy_min_toughness_J`
(15.0 J) is a hard floor: two rows fail it, and both are attractive traps precisely because
they are *cheaper* than the correct answer if toughness is never checked.
`generate_spring_opt.py`'s own solve, run against every row independently (not just the
eligible ones), confirms this directly: the 200 C row (`charpy_impact_J` = 8.0, `S_su_Nmm2`
= 1520.0) solves to cost ~526.42 with `peened` wire -- the single cheapest combination in
the entire table -- and the 300 C row (`charpy_impact_J` = 6.5, `S_su_Nmm2` = 1430.0), which
sits inside this alloy's classical tempered-martensite-embrittlement band (roughly 260-370 C
for many low-alloy steels, where toughness dips even though temper temperature, and so
strength, is not at its lowest), solves to ~598.15 -- also cheaper than the true answer.
Neither row is labeled unsafe anywhere in the data; both simply have a `charpy_impact_J`
value below 15.0 that a solution must actually check, not infer from temper temperature or
hardness. Only after excluding both does the search over the remaining five rows (370 C
through 600 C) crossed with both wire treatments locate the true global minimum: the 370 C
row (`charpy_impact_J` = 18.0, comfortably clearing the floor), combined with `peened`
wire, at cost 675.59 -- deliberately the same `S_su_Nmm2` = 1350.0, `S_se_base_Nmm2` =
420.0, and `tau_allow_Nmm2` = 620.0 this material used before this table existed, so every
other sealed downstream number (the parametric optimum's geometry, the frequency-optimized
alternative, the Pareto candidates, all of it) is unchanged by this feature. The remaining
toughness-passing rows (430 C through 600 C) are progressively weaker and give progressively
higher cost at every treatment, confirming 370 C is not merely toughness-eligible but
actually cost-optimal among the eligible set, not a coincidence of exclusion. `solution/solve.py`
independently re-derives the same search (`analyze_parametric_optimization`'s
`eligible_rows`/`candidates` loop), never importing `generate_spring_opt.py`'s table.

Tempering is a heat treatment applied after the composite is consolidated, which raises a
fair question: shouldn't it relax the residual-stress trap above, rather than leaving
`tau_res` fixed regardless of which row wins? It does not, and deliberately so.
`thermal_residual_shear_Nmm2` models a *coherent CTE-mismatch* stress -- an elastic state set
by the matrix and reinforcement's differing contraction on cooldown from the fully-consolidated,
stress-free state at `T_PROCESS_C` (600 C) to `T_REF_C` (20 C) -- not the matrix's own
quench-hardening *dislocation* structure, which is what tempering acts on and is exactly what
`tempering_response`'s temper-dependent strength/toughness columns already capture. A CTE-mismatch
elastic state re-establishes itself identically on any cooldown to `T_REF_C` as long as the part
is never reheated above the stress-free temperature in between; every `tempering_response` row is
<=600 C, so none of them exceed `T_PROCESS_C`, and `tau_res` is correctly independent of the temper
choice. A temper step hot enough to exceed `T_PROCESS_C` would indeed call this into question --
this table is capped at exactly `T_PROCESS_C` on purpose, so that question never arises.

## The wire-treatment trade-off

Shot peening (`peened`) multiplies the fatigue endurance limit `S_se` (and, for a design
using the finite-life criterion, the Basquin-derived allowable the same way) by 1.35 and
the material's relative cost per unit volume by 1.20; it does not change the static
allowable stress or the ultimate strength `S_su`. Both strengths are also temperature-
derated by 0.15% per degree above the material's 20 C characterization temperature,
evaluated at this latch's 85 C operating temperature (a 9.75% reduction), before either
treatment multiplier is applied and before the composite residual stress above is added to
the mean-stress term. Solved independently, the global minimum-cost design at the
optimum's own active-coil count (~10.28) uses `peened` wire at cost ~675.59, versus
~825.36 for the best achievable `unpeened` design at the same coil count -- despite its 20%
cost premium, shot peening's higher fatigue margin (now including headroom against the
residual-stress penalty and its own process-robustness re-check) allows a smaller, lighter
spring, and the volume saving outweighs the price premium. This does not hold everywhere
on the feasible frontier, though: at higher active-coil counts (the crossover falls between
Na~14.6 and Na~14.7, verified by independently re-solving the min-cost-at-fixed-`Na`
frontier for both treatments) the `peened` branch's thinner, higher-fatigue-margin wire
runs into the process-robustness buckling re-check before the `unpeened` branch does, so
`unpeened` becomes the cheaper feasible option instead -- and past roughly Na~16.3, *neither*
treatment is feasible any more, because the process-robustness re-checks of buckling and
the frequency-margin floor together rule out both branches before the nominal buckling
limit even gets the chance to on its own. Neither branch is uniformly better; both must
actually be solved and compared at the coil count in question, not picked by inspection or
by generalizing from the global optimum alone.

## The fatigue trap

The parametric-optimization stage's requirements include a linear mean/alternating
shear-stress damage criterion (a standard fatigue-design approach: alternating and mean
stress components, each normalized by the material's temperature-derated, treatment-adjusted
endurance limit and ultimate strength respectively, must sum to no more than the reciprocal
of a required safety factor), evaluated for the force the spring cycles between on every
latch actuation, not the single peak force the static stress check uses.
`generate_pareto_candidates.py`'s Q2 and Q3 satisfy every static/geometric requirement, and
even the *nominal* fatigue check, with a comfortable margin -- an analysis that stops there
will call them feasible -- but both fail only the process-robustness re-check of fatigue
(`g9_fatigue`), because their wire diameter, while thick enough for the nominal cyclic-load
fatigue case, is not thick enough once the same manufacturing-tolerance noise the
robust-design stage characterizes is applied in its worst-case (thinner-wire) direction.
Because the fatigue relation depends only on wire and coil diameter (not active-coil
count), Q2 and Q3 -- which differ only in `Na` -- fail it identically.

## The buckling trap

`generate_spring_opt.py`'s buckling requirement is a lateral-buckling slenderness limit:
the spring's free length divided by its mean coil diameter must not exceed a limit that
depends on how the spring's ends are restrained (given as a small table keyed by the
morphological chart's `end_fixation` variant, using the C3 -- squared-and-ground ends --
row this dataset's winning concept selects, limit 4.5). Free length grows with active-coil
count, so this requirement pulls directly against the final-selection stage's own
durability proxy (maximizing `Na`): `pareto_candidate_designs.csv`'s Q11 sits at a large
active-coil count (`Na`=22) and satisfies the static-stress and fatigue requirements
comfortably -- it would look promising to a screen that checks only those -- but fails the
force-delivery floor and both the nominal and process-robustness buckling checks together.
These are not three independent coincidences: at `Na`=22, within the stated diameter
bounds (`d<=2.0` mm, `D<=14.0` mm), no `(d, D)` pair can satisfy the force-delivery floor
without also violating the buckling limit -- the same large free length that a stiff-enough
spring needs at this coil count is exactly the free length that is laterally unstable, so a
screen would find this design fails on multiple fronts at once, not as separate bad luck.
This is also why the global optimum's own treatment choice is not uniform across the
feasible frontier (see "The wire-treatment trade-off" above): the buckling limit, not
fatigue or stress, is what eventually rules out the cheaper treatment branch as active-coil
count rises.

## The surge trap, and its mirror image

`generate_spring_opt.py`'s frequency requirement is a fundamental-natural-frequency floor:
`f_n = (2/pi)*(d/(D^2*Na))*sqrt(G/(32*rho_eff))` (with `rho_eff` the composite's own
rule-of-mixtures density; the `1e6` unit-conversion factor omitted here for readability)
must be at least `frequency_safety_margin` (15) times this latch's actuation rate
(`operating_actuation_frequency_hz`, 20 Hz), i.e. at least 300 Hz, a standard spring-surge
design rule of thumb. This requirement pulls in the *opposite* direction from the buckling
limit above: larger `D` and `Na` (which raise free length and risk buckling) also *lower*
`f_n`, so the two failure modes bound the feasible region from different sides rather than
the same one. At the global cost optimum `f_n` is a comfortable ~586.3 Hz (margin ratio
~29.3, well above the required 15), so this requirement does not move the headline optimum
-- but it is not vestigial: `pareto_candidate_designs.csv`'s Q10 (`D`=14.0, `Na`=11.0, at
the smallest wire diameter that still nominally clears every other requirement) fails only
the process-robustness re-check of the frequency-margin floor -- it comfortably clears the
*nominal* floor but not the worst-case (thinner-wire, higher-`Na`) noise direction that
re-check applies. Q9, by contrast, is built to look like a plausible supplier-catalog slip:
it uses the `(d, D)` that minimizes cost at `Na`=16 but is reported at `Na`=16.3 without
re-optimizing, and fails the force-delivery floor (the spring rate is now too soft for that
`d, D`) *and* the process-robustness buckling re-check together, at the same time -- a
genuine two-cause failure at this end of the frontier, not a single clean trap, because the
force-delivery and buckling-robustness limits are jointly active there. Together, Q9 and
Q10 show the process-robustness re-checks are real, precisely located limits rather than a
coarse cutoff a screen could round away.

Separately, `generate_spring_opt.py` also independently re-solves a *second* optimization at
this stage: the maximum-`f_n` design achievable using the global optimum's own wire
treatment, subject to every other requirement (fatigue and buckling process-robustness
included) except the frequency floor and its own process-robustness re-check, and a cost
cap of `frequency_alternative_cost_cap_multiplier` (1.15) times the minimum-cost design's
own cost -- see "The fatigue-life-philosophy judgment call" above for the two resulting
designs and why they differ. A report that assumes maximizing `f_n` is simply "the same
problem, solved for a different objective" and expects the cost cap itself to bind will not
notice either the genuinely different geometry or that the housing-bore and
force-delivery-cap requirements, not the cost budget, are the actual limit.

## The near-miss and the dominated point

Q1 sits at the same `(D, Na)` as the global cost optimum with wire diameter nudged up past
the force-delivery oversupply cap alone -- it delivers a little more than
`oversupply_factor * F_op_N` at full deflection -- small enough that a candidate list
"trusted" at face value, or a force recomputation carried at low precision, will silently
let it through; every other requirement, nominal and process-robustness alike, still passes
comfortably. Q8 is a different kind of trap: it *is* feasible on every one of the eleven
requirements -- static, fatigue, buckling, frequency-margin, and all three
process-robustness re-checks alike -- sitting at the housing-bore limit (`D`=14.0) with a
large active-coil count (`Na`=10.5), but costs far more (~1544 vs. ~676-705 on the
cost-minimal frontier) and has a far smaller dynamic margin (~15.8 vs. ~27.7-29.6) than the
frontier candidates, so it is strictly dominated -- Q6, for instance, beats it on cost,
durability, *and* dynamic margin all at once. A report that skips genuine Pareto-dominance
filtering and just returns every feasible candidate will include Q8 in
`pareto_optimal_candidates` and fail `tests/test_outputs.py::test_pareto_optimal_set`.

## TOPSIS and the weighted-sum method disagree

Among the four genuinely Pareto-optimal candidates under all three objectives at once (Q4,
Q5, Q6, Q7, the cost-minimal frontier at `Na`=9, 10.28 (the global optimum), 11, and 12),
and with the stated unequal weights (0.45 cost, 0.35 durability, 0.20 frequency margin),
TOPSIS picks Q7 with a clear score margin (~0.81 vs. the next-best ~0.68, Q6), ranking
candidates by geometric distance to the ideal and anti-ideal points across all three
normalized, weighted objectives at once -- Q7 has the highest `Na` (12) and, while its cost
is the highest of the four and its frequency margin the lowest, its balanced overall
standing wins under a geometric-distance metric. The weighted-sum method (min-max
normalized per criterion, same weights) instead picks Q6 (~0.83 vs. Q5's ~0.77) -- linear
scalarization rewards strength concentrated on the heavily-weighted criteria more directly
than TOPSIS's joint-distance ranking does, and Q6 sits closer to the middle of the
frontier's cost/durability/margin trade-off than Q7's more extreme durability-leaning
position. The two methods are not required to agree, and here they do not -- the report
must say so and resolve it rather than silently picking whichever number happened to
compute first. `instruction.md` requires the report to recognize and state this
disagreement explicitly, and `solution/solve.py`'s reference synthesis carries TOPSIS's
winner forward, explaining why, as the method that weighs a candidate's overall standing
jointly rather than crediting strength on two axes independently of a weakness on the
third. `tests/test_outputs.py::test_synthesis_addresses_method_disagreement` checks that
the written explanation says so.

## Anti-hardcoding checks

Because every stage here is a deterministic function of small, human-readable data, a
report could in principle reproduce the sealed numeric targets without genuinely
re-deriving them. `tests/test_outputs.py` guards against this with four recomputation
checks (`test_morphological_matches_raw_chart`, `test_axiomatic_matches_raw_candidates`,
`test_taguchi_matches_raw_csv`, `test_pareto_matches_raw_csv`) that independently rebuild
each stage's key result from the raw data copies in `tests/` using only the Python
standard library -- including a `math.erf`-based standard normal CDF in place of
`scipy.stats.norm`, since the verifier image installs no scientific-computing packages --
and compare it both against `ground_truth.json` and against the agent's own reported
values. A fifth mechanism, `test_parametric_optimum_satisfies_constraints`, independently
recomputes all eleven constraint functions -- five static/geometric, fatigue, buckling, the
frequency floor, and the three process-robustness re-checks, including the composite
residual-stress term inside fatigue and the composite-density-derived frequency floor --
from the agent's own reported `(d, D, Na, treatment)` (using the material/end-fixation rows
this dataset always selects, hardcoded in the test the same way the raw-data checks are),
so a plausible-looking cost that is not actually feasible -- nominally or under
process-robustness noise -- is caught even though it is not a raw-data recomputation in the
same sense as the other four. A sixth and seventh,
`test_parametric_optimum_composite_cte_matches_recomputation` and
`test_parametric_optimum_composite_density_matches_recomputation` /
`test_parametric_optimum_natural_frequency_matches_recomputation`, independently recompute
Turner's effective-CTE model, the rule-of-mixtures density, and the natural-frequency
relation from the same hardcoded matrix/reinforcement constituent properties and compare
them to the agent's reported values, so a value that merely lands close to the sealed
number without having been derived from the constituent data still fails.
`test_frequency_optimized_alternative` additionally recomputes the alternative design's own
feasibility (against every requirement except the frequency floor and its own
process-robustness re-check), cost cap, and natural frequency the same way -- self-
consistently, against whichever fatigue-life philosophy the report itself claims to use
(see "The fatigue-life-philosophy judgment call" above). An eighth,
`test_parametric_optimum_temper_clears_toughness_floor`, looks up whichever `temper_temp_C`
the report names in a hardcoded copy of `tempering_response` and confirms that row's own
`charpy_impact_J` actually clears `CHARPY_MIN_TOUGHNESS_J` -- catching a report that names a
plausible-looking but wrong (trap) tempering condition even where the resulting cost happens
to land close to the sealed value (see "The tempering trap" above).

## A bug caught during authoring

An earlier draft of `tests/ground_truth.json` had `taguchi_best_on_target_run_true` set to
`8` -- the *most-robust* run -- while its paired field,
`taguchi_best_on_target_levels_true`, correctly held `{"A": 3, "B": 1, "C": 3}`, the factor
pattern for run `7`, not run `8`. Caught by cross-checking the two fields against each
other and against a fresh recomputation from `taguchi_spring_robustness.csv` before
`solution/solve.py` was ever written against the file; fixed to `7`.

A second bug, caught during the pass that added the process-robustness requirement: the
generator's own `feasible()` self-check function inverted the sign convention its own
constraint vector uses (`_full_cons_vec` returns positive-is-feasible margins, but
`feasible()` briefly checked `<= tol` instead of `>= -tol`), which silently marked every
genuinely feasible candidate on the new cost-minimal frontier as infeasible even though the
same constraint vector's own failure-listing helper, using the correct direction, showed no
failures for them -- an internally contradictory result (`feasible=False` with
`failing=[]`) that the self-check caught immediately on the next run. Fixed to the correct
direction, with a comment in the source recording the mistake so it is not repeated a third
time.
